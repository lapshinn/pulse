**Версия:** 1.0  
**Статус:** Утверждённая концепция / подготовка к прототипированию  
**Направление:** Compact Minimal  
**Платформы:** Desktop / Tablet / Mobile  
**Темы:** Light / Dark

Ответы на открытые вопросы и предложения по контрасту, порогам устаревания и MediaMetrics: [STAGE_01_DECISIONS.md](STAGE_01_DECISIONS.md). Пока вариант компоновки не выбран, прототип не собирается.

# 1. Цель интерфейса

Personal Dashboard — персональный информационный центр, позволяющий быстро оценить основные события и показатели дня.

Главная задача интерфейса — предоставить пользователю необходимую информацию за 10–15 секунд без необходимости открывать дополнительные разделы.

Основные принципы:

1. Информация важнее декоративных элементов.
2. Основные показатели должны быть видны сразу.
3. Второстепенная информация доступна по нажатию.
4. Новости должны быть заметны, но не перегружать интерфейс.
5. Интерфейс должен одинаково хорошо работать на компьютере и смартфоне.
6. Светлая и тёмная темы должны быть полноценными, а не формально инвертированными.

# 3. Информационная архитектура

Основные разделы:

- Dashboard
- Health
- Weather
- News
- Settings

## Dashboard

Главная страница включает:

1. Шапку с навигацией.
2. Дату, время и приветствие.
3. Погодную карточку.
4. Четыре показателя здоровья.
5. График активности.
6. Пять главных новостей.

## Health

Подробная аналитика:

- шаги;
- сон;
- пульс;
- калории;
- история измерений;
- недельная и месячная динамика.

## Weather

Подробный прогноз:

- текущая погода;
- температура;
- ощущаемая температура;
- ветер;
- влажность;
- осадки;
- прогноз на 7 дней.

## News

Полная новостная лента:

- приоритетные новости;
- категории;
- источник;
- время публикации;
- поиск и фильтрация, если это предусмотрено источником данных.

## Settings

Настройки приложения:

- тема;
- часовой пояс;
- источники данных;
- обновление информации;
- настройки отображения.

# 4. Desktop UI

## 4.1. Общая компоновка

Основной ориентир — экран 1440 × 900 px.

Предлагаемые размеры:

- максимальная ширина контента: 1440 px;
- боковые внутренние отступы: 32 px;
- расстояние между крупными блоками: 24 px;
- расстояние между карточками: 16 px;
- скругление карточек: 12–16 px.

Для широких экранов использовать трёхколоночную композицию. Для ноутбуков — двухколоночную.

## 4.2. Header

Содержимое:

- логотип и название Personal Dashboard;
- навигация;
- текущая дата;
- переключатель темы;
- настройки пользователя.

Шапка должна быть компактной и не занимать чрезмерно много вертикального пространства.

## 4.3. Приветствие и время

Слева:

- текущее время;
- дата;
- краткое приветствие.

Справа:

- город;
- информация о текущем дне или небольшое контекстное сообщение.

Время обновляется без перезагрузки страницы.

## 4.4. Weather Card

Основная информация:

- город;
- температура;
- погодное состояние;
- ощущаемая температура;
- ветер;
- влажность.

Дополнительно — компактный прогноз на ближайшие часы или дни.

Карточка должна быть визуально выразительной, но не конкурировать с новостями.

## 4.5. Health Cards

Ровно четыре карточки:

### Steps

- количество шагов;
- дневная цель;
- процент выполнения;
- индикатор прогресса.

### Sleep

- продолжительность сна;
- время засыпания и пробуждения, если доступно;
- краткая оценка качества, только если она присутствует в исходных данных.

### Heart Rate

- последнее актуальное значение;
- единица измерения — уд/мин;
- время измерения.

### Calories

- активные калории;
- уточнение типа калорий, если источник различает активные и общие.

Карточки должны иметь одинаковую визуальную структуру.

При нажатии открывается соответствующий раздел Health.

## 4.6. Activity Chart

График активности за неделю.

Предусмотреть:

- переключение периода: 7 дней / 30 дней;
- отображение значений;
- выделение текущего дня;
- подсказки при наведении или нажатии;
- адаптивную ширину.

Не использовать чрезмерное количество линий и визуальных эффектов.

## 4.7. News Block

На Dashboard отображаются пять наиболее важных материалов.

Для каждого материала:

- порядковый номер;
- категория;
- заголовок;
- источник;
- дата и время публикации;
- ссылка на оригинальную публикацию.

Изображения не используются.

### Правило сортировки

Новости сортируются по приоритету, а не только по времени публикации.

Приоритет должен определяться серверной логикой или источником данных. Нельзя случайным образом назначать важность материалам.

При наличии нескольких равнозначных материалов допускается дополнительная сортировка по времени публикации.

### Поведение

Нажатие на новость открывает оригинальную страницу источника.

Требования:

- открытие в новой вкладке;
- использование проверенного URL;
- безопасные параметры внешней ссылки;
- отсутствие фиктивных ссылок;
- отсутствие подмены оригинального материала демонстрационным текстом.

Кнопка «Все новости» открывает раздел News.

# 5. Mobile UI

## 5.1. Общая компоновка

Мобильный интерфейс должен быть спроектирован отдельно, а не просто уменьшен до ширины телефона.

Ориентиры:

- ширина: 360–430 px;
- внутренние отступы: 16 px;
- расстояние между карточками: 12 px;
- одна основная колонка;
- компактные заголовки;
- удобные зоны нажатия.

## 5.2. Верхняя навигация

На смартфоне используется верхнее раскрывающееся меню.

В закрытом состоянии:

- логотип;
- название приложения или компактный знак;
- кнопка меню;
- переключатель темы.

В открытом состоянии:

- Dashboard;
- Health;
- Weather;
- News;
- Settings.

После выбора раздела меню закрывается.

Не использовать нижнюю фиксированную навигацию.

## 5.3. Порядок блоков

Мобильная главная страница:

1. Header.
2. Дата и время.
3. Погода.
4. Четыре показателя здоровья в сетке 2 × 2.
5. Активность.
6. Пять главных новостей.
7. Дополнительная информация и служебные элементы.

Новости остаются полноценным блоком и не скрываются в отдельной вкладке.

### Dark Theme

| Text Secondary | #A4ADA9 |
| Border | #39434A |

| Danger | #E18488 |

Цвета должны быть реализованы через дизайн-токены, а не разбросаны по компонентам.

## 6.2. Типографика

Рекомендуется использовать Inter или другую современную нейтральную sans-serif гарнитуру после проверки лицензии и доступности.

Иерархия:

- Page Title: 28–32 px;
- Section Title: 18–22 px;
- Card Value: 24–32 px;
- Card Title: 13–15 px;
- Body: 14–16 px;
- Secondary: 12–13 px.

## 6.3. Иконки

Использовать Lucide Icons.

Иконки должны быть единообразными по толщине и размеру.

Не использовать эмодзи в качестве постоянной замены интерфейсных иконок.

## 6.4. Анимации

Использовать Motion только там, где анимация улучшает восприятие:

- открытие меню;
- переключение темы;
- появление карточек;
- раскрытие интерактивных элементов;
- переходы между состояниями.

Анимации короткие и ненавязчивые.

Учитывать prefers-reduced-motion.

# 7. Состояния интерфейса

Каждый блок должен иметь состояния:

- Loading;
- Success;
- Empty;
- Error;
- Stale Data.

Не показывать нулевые значения, если данные отсутствуют.

Вместо выдуманных показателей использовать понятное сообщение «Нет данных».

Демонстрационные данные должны быть явно помечены как демонстрационные.

Для устаревших данных показывать время последнего обновления.

Ошибки одного источника не должны блокировать отображение остальных блоков Dashboard.

# 8. Адаптивность

Предварительные точки перелома:

- Mobile: до 639 px;
- Tablet: 640–1023 px;
- Desktop: 1024–1439 px;
- Wide Desktop: от 1440 px.

Проверить интерфейс как минимум на следующих размерах:

- 360 × 800;
- 390 × 844;
- 768 × 1024;
- 1024 × 768;
- 1366 × 768;
- 1440 × 900;
- 1920 × 1080.

Не допускать горизонтальной прокрутки на мобильных устройствах.

# 9. Accessibility и UX

Обязательные требования:

- семантическая HTML-разметка;
- управление меню с клавиатуры;
- видимый focus state;
- контраст текста и фона;
- доступные названия иконок и кнопок;
- достаточные области нажатия;
- корректная работа при увеличении масштаба;
- поддержка prefers-reduced-motion.

Важные показатели должны различаться не только цветом, но и текстом или формой.

# 10. Технические ограничения UI

- Компоненты должны быть переиспользуемыми.
- Дизайн-токены централизованы.
- Компоненты не должны содержать бизнес-логику получения внешних данных.
- Не смешивать реальные данные и тестовые.
- Ссылки на новости должны проходить проверку.
- Внешние ссылки открывать безопасно.
- Не хранить секреты во frontend.
- Не создавать фиктивные интеграции.

# 12. Критерии приёмки Этапа 1

Этап считается завершённым, когда:

1. Подготовлены Desktop и Mobile прототипы.
2. Утверждена общая компоновка Dashboard.
3. Утверждены светлая и тёмная темы.
4. Утверждена верхняя мобильная навигация.
5. Утверждены четыре показателя здоровья.
6. Утверждён вид пяти новостных материалов.
7. Определено поведение внешних ссылок.
8. Подготовлена базовая дизайн-система.
9. Описаны основные состояния компонентов.
10. Проверены основные разрешения экрана.
11. Документация обновлена.
12. Пользователь подтвердил результат.

# 13. Что остаётся уточнить перед реализацией

Следующие решения не следует принимать самостоятельно:

- окончательная гарнитура;
- конкретная ширина и высота карточек;
- точный вид погодной карточки;
- визуализация активности;
- алгоритм определения важности новостей;
- конкретный новостной провайдер;
- окончательный вид мобильного меню;
- поведение переключателя часового пояса.

Их необходимо обсудить в рамках Этапа 1.

# 14. Следующий шаг

После согласования этой спецификации:

1. Провести анализ требований и документации.
2. Подготовить два-три варианта детальной компоновки.
3. Создать интерактивный UI-прототип.
4. Проверить Desktop и Mobile.
5. Получить подтверждение пользователя.
6. Только после подтверждения переходить к UI Foundation.

**Важно:** данная спецификация фиксирует направление дизайна, но не разрешает автоматически начинать полноценную разработку приложения.
